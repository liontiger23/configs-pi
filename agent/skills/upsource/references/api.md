# Upsource RPC API reference (verified against upsource.internal)

Official docs: <https://upsource.internal/~api_doc/index.html>
Full reference: <https://upsource.internal/~api_doc/reference/Service.html>

## Transport

- Endpoint: `POST {URL}/~rpc/{Method}`, `Content-Type: application/json`
- Auth: `Authorization: Bearer <token>`. Token sources, in order:
  `$UPSOURCE_CREDENTIALS` (path to a file), saved config
  `~/.config/upsource/hosts.json` (created by `upsource auth login`, chmod 0600,
  keyed by host, stores url/token/user).
  Never display the token.
- Default URL: `--url` flag → `$UPSOURCE_URL` → single saved host in config →
  `https://upsource.internal`.
- `getCurrentUser` `{}` → current user object (`login`, `userId`, permissions);
  used to verify tokens at `auth login`.
- TLS: self-signed cert — the bundled CLI uses an unverified SSL context.
- Responses: `{"result": {...}}` or `{"error": {"code": 100, "message": "..."}}`.
  Code 100 covers both unknown methods and bad request bodies — read the message.
- Error message patterns:
  - `Method 'X' not found` — method does not exist on this server version.
  - `Request message is not initialized. ...SomeDTO` — required DTO fields missing.
  - `Cannot deserialize params` — wrong body shape (usually nesting where flat is needed).

## Quirk: flat DTO bodies — and the inconsistency

Most request DTOs are flattened in JSON. `ReviewIdDTO` has fields
`{projectId, reviewId}` but methods disagree whether it must be nested or flat:

- **Flat** (read-shaped queries): `getReviewDetails`, `getRevisionsInReview`,
  `getReviewSummaryChanges` ← `{"projectId":"proj","reviewId":"PROJ-CR-123"}`
- **Nested** (write/review-object DTOs): `addRevisionToReview`,
  `removeRevisionFromReview`, `createDiscussion` (`reviewId` field is a nested
  `ReviewIdDTO`)
- When deserialization fails (`Cannot deserialize params`), try the other shape.
- Repeated fields keep their proto name even when singular-looking:
  `RevisionsInReviewDTO.revisionId` is an **array** of revision ids.
- Exception: fields that are genuinely message-typed stay nested, e.g.
  `CreateDiscussionRequestDTO.reviewId` is a nested `ReviewIdDTO`.

## Verified label API (2026-11-05; decided: NOT used — text tag is the convention)

- `getLabels {"projectId"}` → `LabelsListDTO` (predefined: bug, code style,
  enhancement, explanation, help wanted).
- `addDiscussionLabel {"projectId","discussionId","label":{"name":"x"}}` →
  LabelDTO. Arbitrary names are accepted and auto-created (returns a UUID `id`).
- `removeDiscussionLabel` — **requires `label.id`** (the UUID from the add);
  name-only gives `HTTP 500: Assertion failed`.
- Quirks: `getLabels` never lists ad-hoc labels; `label:` search query is
  unsupported (0 results); one ad-hoc add returned success but the discussion
  listing lagged/inconsistent. Backend too flaky for agent workflows — this is
  why the `[ai]` text tag (see SKILL.md) is the human/agent marker instead.
- Review-level twins (`getReviewLabels`, `addReviewLabel`, `removeReviewLabel`,
  `createOrEditLabel`) exist in the catalog; untested live.
- Callable ad hoc via `upsource call ...` (see below).

## Embedded catalog (authoritative for "does method X exist?")

The full API reference is embedded in the CLI (from `~api_doc`, regenerated by
`tools/extract_api.py` → `tools/catalog.json` → `tools/embed_catalog.py`):

```bash
upsource api [pattern]        # 174 methods: name(req) -> resp + description
upsource api-show <name>      # method or DTO with all fields (types, required)
upsource call <Method> k=v [k2.v2=x ...] [--dry] [--allow-unknown]
```

`call` validates against the catalog: unknown top-level fields and missing
required fields are errors (bypass with `--allow-unknown`); dotted paths build
nested messages; values coerce by type. It still cannot know the flat/nested
server quirks — verified shapes stay in this file; `raw` remains the
no-validation escape hatch.

Before claiming "the API has no method for X": `upsource api -i <keyword>` —
never a hand-rolled regex over doc HTML (that is how label support was missed
once).

## Verified methods (HTTP 200 with a real payload)

| Method | Body (flat) | Notes |
|---|---|---|
| `getAllProjects` | `{"limit":100}` | result `project[]` |
| `getReviews` | `{"projectId":"proj","limit":20,"query":"state: open"?}` | result `reviews[]`; query optional |
| `getReviewDetails` | `{"projectId","reviewId"}` | full review incl. `revisions[]`, `participants[]` |
| `getProjectDiscussions` | `{"projectId","query":"review: PROJ-CR-123","limit":100,"skip":0}` | **list a review's threads**; result `discussions[]`, `hasMore` |
| `getUserInfo` | `{"ids":["<uuid>",...]}` | batch; result `infos[]` with `name`, `login`, `isMe` |
| `getRevisionInfo` | `RevisionInProjectDTO` | not yet exercised |
| `getFeed` | `{"limit","type":FeedTypeEnum,...}` | news feed; not yet exercised |
| `getBranches` | `{"projectId","query":"<prefix>","limit":1000}` | branch names carry `#<repo-alias>` suffix; `reviewId` set on the review-tracked branch; no pagination — use limit 1000 |
| `getRevisionsListFiltered` | `{"projectId","query":"branch: \"name#alias\"","limit","skip"?}` | quote the branch — unquoted `#` → `Unknown subquery` error |
| `getRevisionsInReview` | `{"projectId","reviewId"}` (flat) | result `allRevisions.revision[]`, `newRevisions`, `hasMissingRevisions` |
| `addRevisionToReview` | `{"reviewId":{"projectId","reviewId"},"revisionId":["<upsourced-id>",...]}` | **nested** reviewId; repeated field is `revisionId` (NOT `revisions`); returns VoidMessage `{}` |
| `removeRevisionFromReview` | same shape as addRevisionToReview | untested live (don't detach real work) |
| `getSuggestedRevisionsForReview` | `{"projectId","reviewId"}` | returned empty for the test review; low value |
| `startBranchTracking` | `{"reviewId":{...},"branch":"..."}` | only for converting a non-tracking review; ERRORS `Review cannot be converted to a branch review` if review already tracks a branch |
| `addComment` | `{"projectId","discussionId","text","parentId"?}` | **reply to a thread**; result CommentDTO |
| `createDiscussion` | `{"projectId","anchor":{},"text","reviewId":{"projectId","reviewId"}}` | new thread; empty `anchor` = review summary |
| `resolveDiscussion` | `{"projectId","discussionId","isResolved":bool}` | reviewer resolves, not the agent (by policy) |
| `updateComment`, `removeComment` | see docs | etiquette: don't touch others' comments |
| `readDiscussion`, `starDiscussion` | `UpdateDiscussionFlagRequestDTO` | not needed by agent |

Not available on this server (verified 400): `getReviewInfo`, `getReviewComments`,
`getDiscussions*`, `startNewDiscussion`, `changeDiscussionState`, `writeComment`,
`addReviewComment`, `replyToComment`, `getReviewChanges`, `getReviewHistory`.

## Key DTO shapes (from ~api_doc)

- `DiscussionInFileDTO`: `discussionId`, `anchor{fileId,revisionId,range{startOffset,endOffset}}`,
  `comments[]`, `isResolved`, `labels[]`, `review` (ShortReviewInfoDTO)
- `CommentDTO`: `discussionId`, `commentId`, `text`, `authorId`, `date` (ms epoch),
  `parentId?`, `isEditable`, `isRead`
- `AnchorDTO`: `range?{startOffset,endOffset}`, `fileId?`, `revisionId?`, `inlineInRevision?`
- `ReviewIdDTO`: `projectId` + `reviewId` (e.g. `proj` + `PROJ-CR-123`)
- Review state enum: 1=open, 2=closed. Participant role: 1=author, 2=reviewer, 3=watcher;
  state: 1=none, 2=accepted, 3=concern, 4=seen, 5=pending

## Conventions

- Project id from review id: prefix before first `-`, lowercased (`PROJ-CR-123` → `proj`).
- Review web URL: `{URL}/{projectId}/review/{reviewId}`.
- "Fixed" replies are plain comment text; the **reviewer** resolves the thread.
